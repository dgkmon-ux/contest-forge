# ④ report — 제출문서·발표덱·대본

입력: `plan.md`, `mvp/`, `brief.md`(제출 규격), `rubric.md`
출력: `submission.md`, `deck.html`, `script.md`, (조건부) `video-storyboard.md`

> **ai-nativeness 유형은 이 단계를 쓰지 않는다.** 제출물이 코드·커밋·로그이므로 `3-mvp.md` §5의 제출 직전 체크로 끝난다.

**`brief.md`의 제출물 목록에 있는 것만 만든다.** 발표가 없는 서류 전형이면 `deck.html`·`script.md`를 만들지 않는다. 다음 라운드 대비로 미리 필요하면 사용자에게 먼저 묻는다.

---

## 1. submission.md — 규격이 내용보다 먼저다

**먼저 `brief.md`의 "제출 규격"을 확인한다.** 비어 있으면 사용자에게 묻는다. 규격을 모른 채 쓰면 다시 써야 한다.

작성 순서:
1. 요강이 지정한 **항목 구성과 순서를 그대로** 따른다. 임의로 추가·삭제·개명하지 않는다.
2. `plan.md`에서 해당 항목에 맞는 내용을 가져와 분량에 맞게 압축한다.
3. 지정 양식 파일(HWP/DOCX)이 있으면 그 항목명에 맞춰 `submission.md`를 쓰고, "이 내용을 양식 파일에 옮겨 붙이세요"라고 안내한다. HWP는 직접 만들 수 없다.

작성 후 **자체 검사**를 돌리고 결과를 보고한다:

```
제출 규격 검사
 ✓ 요구 항목 7개 모두 포함
 ✗ 분량: A4 5장 제한 / 현재 9,400자 ≈ 6장 → §4 모듈 설명 압축 필요
 ✓ 파일명 규칙 준수
 ✓ 개인정보 미포함 (블라인드 심사)
 ⚠ [출처 필요] 2건, [사용자 입력 필요] 1건 남음
```

분량은 **공백 포함 자수**로 세고 환산한다 — A4 서술체 약 1,400~1,800자/장, PPT 1장 = 슬라이드 1장. "6.2장" 같은 소수점 정밀도는 만들어낼 수 없으니 자수를 함께 표기한다.

블라인드 심사면 소속·이름·팀명·특정 가능한 표현이 없는지 확인한다.

## 2. deck.html — 16:9 자체완결형 슬라이드

### 기본 8장 구성

요강에 페이지 수 지정이 있으면 그것을 따른다. 없으면 이 구성이 기본이다.

| # | 슬라이드 | 내용 |
|---|---|---|
| 1 | 표지 | 서비스명 + **원라인 피치** (plan.md §15) |
| 2 | 문제 | 페인포인트 + **기존 수단으로 왜 안 되는지** (§2) |
| 3 | 프레임 전환 | "A의 시대를 넘어 B로" — 이 발표의 한 문장 (plan.md 서두 인용문) |
| 4 | 솔루션 구조 | 파이프라인·아키텍처 도해 (§3, §8) |
| 5 | 데모 | **OFF/ON 비교표** + 핵심 화면 (§6) |
| 6 | 차별성 | 기존 범주 3개 대비 + "단순 결합이 아닌 이유" (§10) |
| 7 | 지표·로드맵 | 측정방법 + 개발 단계 (§9, §13) |
| 8 | 마무리 | 마무리 메시지 + 원라인 피치 반복 (§14) |

5번이 발표의 정점이다. 여기에 가장 많은 시간을 배분한다.

**화면을 스크린샷으로 넣지 않는다.** 에이전트는 `demo.html`을 캡처할 수 없고, 자체완결 규칙상 외부 이미지 참조도 금지다. 대신 **핵심 화면 1~2개를 deck 안에 HTML로 축약 재구성**한다(판정 상세 화면, 대시보드 카드 등). 실물 캡처를 쓰고 싶으면 사용자에게 스크린샷을 요청해 base64 data URI로 인라인한다.

### 디자인 규칙

- 자체완결형 단일 HTML. 외부 CSS/JS/폰트 링크 금지.
- **이모지 금지.** 데이터 저널리즘 미학 — 절제된 타이포, 넉넉한 여백, 표와 구조로 말한다.
- 슬라이드당 메시지 하나. 문장이 아니라 구절로.
- 16:9 고정 비율, 키보드 좌우 이동, 인쇄 시 슬라이드당 1페이지(`@page { size: 297mm 167mm; }` 계열).
- 색은 최소한으로. 강조색 1개 + 무채색. OFF/ON 비교에서만 대비색을 쓴다.

## 3. script.md — 대본과 질의응답

### 대본
슬라이드별로 **말할 문장 그대로** + 소요 초를 적는다. 총 시간은 요강의 발표 시간에 맞춘다.

```markdown
### 슬라이드 3 — 프레임 전환 (40초)
> "지금까지 금융은 거래를 요청한 사람이 본인인지 확인해 왔습니다.
>  그러나 앞으로는 내가 등록한 AI가 나를 대신해 금융행위를 합니다.
>  이제 확인해야 할 것은 신원만이 아니라 위임받은 권한입니다."

[전환] 다음 장에서 구조를 보여준다
```

`plan.md` §14의 발표 메시지(시작/데모 전환/마무리)를 재료로 쓴다.

### 예상 질문 10개

`plan.md` §12 위험요인·대응 표에서 자동 파생시킨다. 심사위원은 대개 그 표의 항목을 그대로 묻는다.

**답변은 3단계 구조로 고정한다:**

1. **구체적 약점 지점 지목** — "네, ○○ 모듈의 △△ 처리가 그렇습니다." 일반론이나 회피 금지.
2. **왜 위험한지 파급 설명** — 어떤 조건에서 어떤 결과로 번지는가.
3. **다음에 뭘 검증·개선할지 계획** — 구체적 검증 방법까지.

이 구조는 AI 활용역량 평가에서 쓰이는 확인 문제 모범답안 형식과 같다. 약점을 인정하고 통제 계획을 제시하는 쪽이 방어보다 항상 높은 점수를 받는다.

```markdown
### Q. 기능 범위가 너무 넓어 보입니다. 다 만들 수 있나요?
1. 지목 — 맞습니다. 4개 모듈 중 마이데이터 연동은 이번에 구현하지 않았습니다.
2. 파급 — 실제 기관 연동은 승인 절차만 수 개월이라 대회 기간에 불가능하고,
   억지로 넣으면 나머지 3개 모듈의 완성도가 떨어집니다.
3. 계획 — 그래서 공통 정책 엔진 위에 시뮬레이션까지만 구현했습니다.
   실 연동은 <검증 방법>으로 단계 확인 후 확장합니다.
```

질문 유형은 최소 이 넷을 덮는다: 차별성("이미 있지 않나"), 실현가능성("정말 되나"), 범위("너무 넓다"), 검증("어떻게 증명하나").

## 3.5 video-storyboard.md — 시연 영상이 필수인 경우만

`brief.md`에 시연 영상 요구가 있으면 만든다. 촬영은 사용자 몫이지만 콘티와 내레이션까지는 만들어 준다.

```markdown
| # | 초 | 화면 | 내레이션 | 자막 |
|---|---|---|---|---|
| 1 | 0-8 | 표지 | "<원라인 피치>" | 서비스명 |
| 2 | 8-25 | 문제 상황 재현 | ... | |
| 3 | 25-70 | demo.html 시나리오 조작 | ... | 조작 지점 표시 |
```

- 총 길이를 요강 제한에 맞춘다. 초과분은 문제 설명에서 깎고 데모는 남긴다.
- `plan.md` §6 데모 시나리오와 `script.md`에서 파생시킨다. 새로 쓰지 않는다.
- 영상 길이의 절반 이상을 실제 동작 화면에 배분한다.
