# ② ideate — 리서치 3축과 아이디어 수렴

입력: `brief.md`, `rubric.md`
출력: `research.md`, `ideas.md`
끝에 **반드시 멈춘다.** 사용자가 1개를 고르기 전까지 ③으로 가지 않는다.

---

## 1. 리서치 3축

WebSearch를 축별로 병렬 호출한다. 기본은 가볍게 — 축당 2~4회 검색이면 충분하다.

사용자가 "딥으로", "제대로 파봐"라고 하면 승급한다. **설치된 딥리서치 스킬(예: `agent-reach`, `real-deep-research`)이 있으면 그것을 쓰고, 없으면 WebSearch 횟수를 축당 6~10회로 늘린다.**

### 축 ① 주최사 시그널 — 가장 중요
공모전은 참신함보다 **주최사가 원하는 답을 맞히는 것**에서 갈린다.

- 역대 수상작·수상팀 (몇 회차인지, 어떤 주제가 뽑혔는지)
- 주최사 최근 보도자료·사업방향·중점 추진과제
- 주최 부서가 무엇으로 성과를 평가받는지
- 요강 문구에서 반복되는 키워드

→ **"이 주최사는 이런 걸 뽑는다" 가설 3문장**으로 수렴시킨다. 이 가설이 이후 채점의 숨은 가중치가 된다.

#### 역대 수상작이 없을 때 — 폴백 사다리

1회차 대회이거나, 회차는 쌓였는데 수상작을 공개하지 않는 주최사가 많다. **없으면 없다고 적고 아래로 내려간다.** 지어내거나 유사 대회 수상작으로 대신하지 않는다.

| 단계 | 근거 | 가설 신뢰도 **상한** |
|---|---|---|
| 1 | 역대 수상작·심사평 | **상** |
| 2 | 주최 기관의 당해 연도 업무계획·시정방향·보도자료 | **중상** |
| 3 | 주최 **부서**의 소관 사업·최근 발주·조직 목표 | **중** |
| 4 | 요강 문구에서 반복되는 키워드, 지정과제 배경 설명문 | **중** |
| 5 | 아무것도 못 찾음 | **하** — 축①을 채점의 가중치로 쓰지 않는다 |

`research.md`의 가설 문장마다 **몇 단계 근거인지와 신뢰도**를 적는다. `ideas.md`의 `주최사 적합도` 컬럼은 이 신뢰도를 넘을 수 없다 — 4단계 근거로 "적합도 높음·신뢰도 상"을 매기지 않는다.

한 단계 내려갈 때마다 **아이디어 선택을 축①에 의존하는 정도를 줄인다.** 3단계 이하면 게이트에서 사용자에게 "주최사 취향을 추정할 근거가 얇다"고 명시적으로 알린다.

### 축 ② 도메인 현황
- 기존 서비스·솔루션 3~5개와 각각의 한계
- 최근 1~2년 규제·정책 변화
- **빈틈**: 아무도 안 하고 있는데 이유가 있는가, 아니면 그냥 안 한 건가

### 축 ③ 가용 자원
- 쓸 수 있는 공공데이터·API (공공데이터포털, 기상청 API허브, 금융 오픈API 등)
- 인증·신청 절차와 소요 기간 — **대회 기간 안에 못 받는 데이터는 쓸 수 없다**
- 오픈소스·기존 모델

### research.md 형식

```markdown
# 리서치 — <공모전명>

## ① 주최사 시그널
### 역대 수상작
| 회차 | 수상작 | 특징 |
### 주최사 방향
- ... [출처](URL)
### 가설
> 이 주최사는 (A)를 뽑는다. 근거: ...

## ② 도메인 현황
| 기존 서비스 | 무엇을 하나 | 한계 |
### 빈틈
- ...

## ③ 가용 자원
| 데이터·API | 접근 방법 | 소요 기간 | 대회 내 가능? |

## 출처
1. [제목](URL) — 확인일 YYYY-MM-DD
```

모든 사실 주장에 출처 URL을 단다. 검색으로 못 찾은 것은 쓰지 않는다.

## 2. 발산 12개

**4축 × 3개.** 축을 강제해야 다양성이 나온다. 아래가 기본축이며, 공모전 주제에 따라 갈아끼워도 된다(갈아끼웠으면 ideas.md에 명시).

| 축 | 발상 프롬프트 |
|---|---|
| 데이터 주도 | 축③의 데이터를 남들이 안 쓰는 방식으로 결합하면? |
| 사용자 경험 | 기존 서비스가 사용자를 고생시키는 지점을 없애면? |
| 업무 자동화 | 주최사·현업이 지금 사람 손으로 하는 일은? |
| 사각지대 | 아무도 대상으로 안 삼는 사용자·상황은? |

각 아이디어는 이 형식 한 줄:

```
[07] 이름 — 누가(타겟) 무엇을(문제) 어떻게(해결) 한 문장
```

### 사용자가 이미 기획안을 들고 온 경우

기존 기획서·초안·아이디어 메모를 함께 받았다면, **발산 목록에 번호를 붙여 편입하고 나머지와 똑같이 채점한다.**

- 별도 비교표를 만들지 않는다. "기존 안 vs 새 안" 구도를 만드는 순간 채점이 아니라 변론이 된다.
- 기존 안이 여러 개면 각각 별도 번호를 준다. 합치지 않는다.
- 편입한 기존 안은 12개 정원에 **포함**시킨다. 기존 안 2개를 받았으면 새로 10개를 낸다.
- 기존 안이 상위 3개에 들면 견적서를 똑같이 쓴다. **`⚠ 최대 약점`도 똑같이 쓴다** — 사용자가 가져온 안이라고 봐주지 않는다.
- 기존 안의 결론·권고·자체 평가는 **검토할 가설**이지 입력값이 아니다. 그 결론을 근거로 점수를 주지 않는다.

`ideas.md`에 어느 번호가 기존 안인지 표시하고, 채점 후 **"기존 안이 왜 그 순위인지"를 한 단락**으로 적는다. 밀렸다면 어느 항목에서 몇 점을 잃었는지까지. 사용자가 가장 알고 싶어 하는 것이 그것이고, 그 항목이 회복 가능한지 아닌지가 `유지 / 축소 / 폐기`를 가른다.

## 3. 채점

`rubric.md`의 항목과 배점을 그대로 써서 12개를 채점한다.

- 점수는 **모델의 자기추정**이다. ideas.md 상단에 그렇게 명시한다.
- '실현가능성'은 팀 스펙이 아니라 **대회 기간·제출 형식 안에서 동작하는 데모를 만들 수 있는가**로 매긴다. 외부 승인·실계약·모델 신규 학습이 필요하면 감점.

**공식 배점에 없는 것을 점수로 만들지 않는다.** 주최사 선호, 데이터 활용도, 트렌드 부합 같은 숨은 가중치는 실제로 존재하지만, 그걸 배점에 섞으면 요강이 정한 순위를 조용히 뒤집는다. 별도 컬럼으로 분리한다.

```markdown
| # | 이름 | <항목1>/<배점> | ... | 합/<총점> | 주최사 적합도 | 신뢰도 | 근거 |
|---|---|---|---|---|---|---|---|
| 07 | ... | | | | 높음 | 중 | 3회차 수상작 2건이 같은 축 [출처] |
```

- **주최사 적합도** — 높음/중간/낮음. 축① 가설 대비
- **신뢰도** — 상/중/하. 근거가 실제 수상작·공식 문서면 상, 정황 추론이면 하
- **근거** — 출처 URL. 근거를 못 대면 적합도를 비운다

합계 점수가 비슷할 때 이 컬럼으로 가른다. 점수를 이 컬럼으로 조정하지는 않는다.

**컬럼은 `rubric.md`의 항목명과 배점을 그대로 옮긴다.** 아래 헤더를 복사하지 말 것 — 유형마다 항목 수도 배점도 다르다.

```markdown
| # | 이름 | <항목1>/<배점> | <항목2>/<배점> | ... | 합/<총점> | 주최사 적합 |
|---|---|---|---|---|---|---|
| 07 | ... | | | | | ○ |
```

## 4. 상위 3개 견적서 (각 반 페이지)

**먼저 각 안에 대해 표적 재검색을 한다 (안당 1~2회).** "○○ 서비스", "○○ 앱", "○○ 특허" 로 이미 나와 있는지 확인한다. 축②의 사전 리서치는 발산 이전이라 개별 안의 중복을 못 잡는다. "이미 있는 거 아니냐"가 최대 탈락 사유인데 그걸 견적서 단계에서 걸러야 한다.

풀기획안은 쓰지 않는다. 고르는 데 필요한 것만 쓴다.

```markdown
### [07] 이름
- **프레임 전환 한 문장** — 심사위원 머리에 박힐 대비 문장
  예: "본인확인의 시대를 넘어, 위임확인의 시대로"
- **핵심 모듈 3~4개** — 각 한 줄
- **데모 한 장면** — 발표에서 보여줄 결정적 순간 하나
- **차별점** — 기존 서비스 대비 무엇이 다른가 (research 축② 참조)
- ⚠ **최대 약점 1개** — 심사위원이 가장 먼저 찌를 곳. 방어 가능한지도 함께.
- **약점 해소 비용** — 그 약점이 진짜인지 **지금 얼마 만에 확인할 수 있는가.** 아래 3줄 중 하나로.
  - `선확인 가능 (n시간/n일)` — 무엇을 하면 판정되는지 한 줄로 적는다
  - `대회 기간 내 확인 불가` — 그러면 이 약점은 가정으로 안고 가야 한다
  - `확인 불필요` — 이미 판정된 사실
- 예상 구현 난이도: 상/중/하 + 이유
```

**약점 항목을 비워두지 않는다.** 자기채점 편향을 막는 유일한 장치다.

**「약점 해소 비용」이 게이트의 선택지를 바꾼다.** 추천안의 최대 약점이 `선확인 가능`이면, 사용자는 "지금 고른다"와 **"먼저 확인하고 고른다"** 중에서 고를 수 있다. 확인 비용이 대회 기간 대비 작으면(예: D-18에 1일) 확인을 먼저 권한다 — 잘못된 선택을 늦게 발견하는 것보다 훨씬 싸다.

## 5. 게이트 🚧 — 정지

세 안을 나란히 놓고 사용자에게 선택을 요청한다. 추천 1개를 제시하되 이유를 밝힌다.

함께 제시할 것:

- **추천을 뒤집을 조건** — 무엇이 확인되면 다른 안이 낫는가
- 추천안의 약점이 `선확인 가능`이면 **"먼저 확인하고 고르기"를 선택지로 함께 제시**한다
- 축① 근거가 3단계 이하였으면 "주최사 취향 추정 근거가 얇다"고 명시

사용자가 고르기 전에는 `plan.md`를 만들지 않는다. "섞어서 가자"고 하면 어떻게 섞을지 한 번 더 확인한 뒤 진행한다.

선택 결과와 그 이유를 `STATE.md`에 기록하고 `current_stage: ③mvp`로 갱신한다. **탈락한 2개도 이름과 탈락 사유를 남긴다** — 나중에 심사위원이 그 방향을 물으면 답이 있어야 한다.
