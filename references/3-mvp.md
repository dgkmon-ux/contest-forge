## 1. plan.md — 15섹션 풀기획안

`assets/plan.template.md`를 골격으로 쓴다. 선택된 1개 안만 이 깊이로 쓴다.

작성 원칙:

- **§2 문제 정의에서 "기존 수단으로 왜 안 되는지"까지 못박는다.** 문제만 나열하면 "그거 이미 있는 거 아니냐"에 죽는다.
- **§3에 데이터 모델 표를 반드시 넣는다.** 아이디어를 스키마로 내려야 구현 가능함이 증명된다.
- **§4 모듈은 서로 다른 감점축을 덮도록 배분한다.** 목적은 배분이지 특정 역할명이 아니다. 템플릿의 "핵심차별화 / 사회적 공감 / 제도·확장 / 공통 위험신호"는 SaaS·플랫폼형에서 나온 예시일 뿐이다. 정책 제안·데이터 분석·물리 제품·콘텐츠·단일 기능 서비스라면 그 주제에 맞는 역할로 재명명하거나 개수를 줄인다. **해당 없는 역할을 억지로 채우면 오히려 감점이다.**
- **§5에 제외·축소 범위를 명시한다.** 과대약속 방어. 무엇을 안 할지 쓴 문서가 신뢰를 얻는다.
- **§9 성과지표는 숫자가 아니라 측정방법으로 쓴다.** (SKILL.md §4.2)
- **§12 위험요인·대응 표는 심사위원 반론의 선제 방어다.** ②단계 견적서의 "최대 약점"을 여기서 정면으로 다룬다.
- 모든 수치에 출처. 없으면 `[출처 필요]`.

작성 후 미해결 `[출처 필요]` 목록을 사용자에게 별도 보고한다.

## 2. 유형별 구현 분기

### idea-contest → `mvp/demo.html` 단일 목업

- 자체완결형 단일 HTML. 외부 CSS/JS/폰트 링크 금지.
- 클릭으로 시나리오가 진행되도록 한다. 정적 목업보다 훨씬 강하다.
- 메인 루프가 직접 작성한다(위임하지 않음).

**화면 구성은 아이디어 형태를 따른다.** 아래는 유형별 기본값이며, 해당 없는 화면을 억지로 만들지 않는다.

| 아이디어 형태 | 기본 화면 | 결정적 연출 |
|---|---|---|
| 서비스·플랫폼 (탐지·통제·중개) | 사용자 화면 / 관제 화면 / 판단 상세 | **OFF/ON 비교** — 솔루션 없을 때와 있을 때 |
| 데이터 분석·시각화 | 대시보드 / 드릴다운 / 인사이트 카드 | 데이터가 드러내는 반직관적 사실 하나 |
| 정책·제도 제안 | 현행 vs 제안 흐름도 / 이해관계자 영향표 | 제도 적용 전후 시나리오 |
| B2C 앱·콘텐츠 | 온보딩 / 핵심 사용 순간 / 결과 | 사용자 여정 3컷 |
| 단일 기능 도구 | 입력 → 처리 → 출력 한 화면 | 처리 과정을 보이게 만들기 |
| 물리 제품·하드웨어 | 제품 렌더 / 동작 흐름 / 연동 앱 | 사용 상황 재현 |

OFF/ON 비교는 **"문제가 방치된 상태"와 "해결된 상태"의 대비가 성립하는 주제에서만** 강력하다. 데이터 분석이나 콘텐츠 제안에 억지로 붙이면 어색하다 — 그 경우 오른쪽 열의 다른 연출을 쓴다.

### hackathon → `mvp/` 실제 실행 가능 레포

- §3 위임 절차를 따른다.
- 필수: README(설치·실행 3줄 이내), 시드 합성 데이터, 시나리오 e2e 재현 스크립트
- 심사위원이 5분 안에 돌려볼 수 있어야 한다. 환경 구축이 복잡하면 감점이다.

### startup-grant → 목업 + 사업성 자료

- `mvp/demo.html` (위 idea-contest와 동일)
- `mvp/business.md`: 시장 규모(출처 필수), 수익 모델, 원가 구조, 3년 로드맵, 필요 자금 사용처
- 시장 규모를 못 찾으면 `[출처 필요]`. 추정치를 지어내면 사업계획 심사에서 즉사한다.
- **팀·대표자 항목은 작성하지 않는다.** 이 스킬은 팀 프로필을 받지 않으므로 지어낼 수밖에 없는데, 정부 창업지원사업은 팀 축이 독립 배점(통상 20%)이고 대면 평가에서 바로 검증된다. `[사용자 입력 필요: 팀 구성]`, `[사용자 입력 필요: 대표자 이력]` 마커로 남기고 산출 보고 시 목록으로 요청한다.

## 3. 실제 레포 위임 절차

1. `mvp/HANDOFF.md` 작성:

```markdown
# 구현 핸드오프

## 목표
한 문장.

## 스코프
### 만든다
- ...
### 만들지 않는다
- ...  (plan.md §5 제외범위와 일치시킬 것)

## 기술 스택
(이유 포함. 심사위원이 돌려볼 수 있는 최소 의존성을 우선)

## 데이터 모델
(plan.md §3 표를 그대로)

## 수용 기준
- [ ] 시나리오 1: ... 가 ... 하면 ... 가 된다
- [ ] 시나리오 2: ...

## 검증 명령어
```
npm test
npm run demo:scenario-2
```

## 금지사항
- 실제 개인정보·실거래 데이터 사용 금지 (합성 데이터만)
- 외부 유료 API 호출 금지
- 수용 기준에 없는 기능 추가 금지
```

2. `Agent(model: "opus")`로 위임한다. 독립 모듈이 여럿이면 병렬로 띄운다.
3. 메인 루프가 검수한다. **코드 스타일은 보지 않는다** — 심사 대상이 아니다. 대신 아래 품질 게이트를 실제로 돌린다. 전부 통과해야 ④로 간다.

```
제출 전 품질 게이트
 [ ] 클린 환경 설치 — 새 폴더에 clone → README대로만 실행해서 뜨는가
 [ ] 빌드·타입 검사 통과
 [ ] 테스트 통과 (단위·통합·e2e)
 [ ] 시드 데이터 초기화 — 한 번 더 돌려도 같은 상태에서 시작하는가
 [ ] 수용 기준의 시나리오 전부 재현
 [ ] 오류 복구 — 잘못된 입력·빈 데이터에서 죽지 않고 메시지가 뜨는가
 [ ] 시크릿·개인정보 스캔 — .env, 토큰, 실데이터가 커밋에 없는가
 [ ] 심사위원 소요 시간 5분 이내
```

**조건부**
- 요강이 모바일을 요구하거나 심사가 현장 모바일 시연이면 → 핵심 화면 모바일 확인
- 라이브 데모가 있으면 → **실패 대비 녹화본**을 미리 찍어 둔다. 시연 중 죽으면 회복이 안 된다

게이트가 하나라도 깨지면 새 기능을 추가하지 않고 그것부터 고친다.

## 4. ai-nativeness 모드 — 현장 과제형

**`②ideate`만 건너뛴다.** `①recon`은 경량으로 이미 수행돼 있어야 한다 — 대회명·일정·트랙·심사방식을 채운 `brief.md`와 `STATE.md`, `INDEX.md` 행이 있어야 여기 들어올 수 있다(`1-recon.md` §5). 없으면 먼저 `1-recon.md`로 돌아간다.

입력은 **현장에서 받은 과제 문장**이다.

### 4.1 이 트랙에서 점수는 결과물이 아니라 흔적에서 나온다

AI 심사자가 **코드·커밋·대화 로그를 직접 읽고, 문서에 적힌 것과 실제 코드·커밋이 연결되는지 대조**한다. 잘 도는 코드가 있어도 흔적이 없으면 의도·인지·소통 축이 통째로 빈다.

`assets/rubrics/ai-nativeness.md`를 읽고 시작한다.

### 4.2 강제 산출물 — 증거 5축

작업 **시작 시점에** 아래를 만들고, 진행하면서 계속 갱신한다. 끝나고 몰아서 쓰면 커밋 로그와 어긋나 대조에서 걸린다.

**위치: 제출 레포 루트.** `~/contests/<slug>/`가 아니다. AI 심사자가 읽는 것은 제출 레포이므로 증거가 레포 밖에 있으면 없는 것과 같다.

**① `INTENT.md` — 의도 관리 축(100점, 변별력 최대)**
```markdown
## 목표 (Output 구체화)
무엇이 완성인가. 관찰 가능한 형태로.
## 제약
시간 / 금지 / 환경
## 비목표
이번에 안 하는 것과 그 이유
## 수용 기준
- [ ] 검증 가능한 문장으로
## 작업 분해
1. ... → 위임 단위 / 검증 방법
2. ...
## 의도 갱신 로그
- HH:MM 과제 해석 변경: ... 이유: ...
```
과제 해석이 바뀔 때마다 **갱신 로그에 남긴다.** "의도 갱신 및 맥락 유지"가 채점 항목이다.

**② 커밋 규약 — 기술·의도 축**

커밋 메시지 본문에 세 줄을 넣는다.
```
<제목>

why: 무엇을 해결하려 했는가
제약: 어떤 제약 아래 이 선택을 했는가
검증: 어떻게 확인했는가 (명령어 또는 관찰)
```
작게 자주 커밋한다. 한 방 커밋은 과정 증거를 통째로 날린다.

**③ 검증 루프 — 의도 축 "검증 루프 설계 및 통제"**
- 테스트·실행 명령을 **실제로 돌리고** 로그를 제출 레포 루트의 `verification.log`에 남긴다.
- AI 산출물을 그대로 신뢰하지 않았다는 증거가 된다.
- 실패 → 수정 → 재검증 사이클이 로그에 보이는 것이 이상적이다. 실패를 지우지 않는다.

**④ `COGNITION.md` — 인지 관리 축(100점, 대체로 가장 낮게 나오는 축)**

여기가 차별화 지점이다. 아무도 못 채운 축이므로 채우면 바로 벌어진다.
```markdown
## 이 구조가 어디서 깨지는가
- 입력이 ... 이면 ... 에서 실패한다. 근거: <파일:줄>
## AI가 이렇게 결정한 근거
- ... 를 택했다. AI가 제시한 이유는 ... 이고, 내가 검증한 결과 ...
- 내가 받아들이지 않고 바꾼 지점: ...
## 예상 리스크 3개
| 리스크 | 발생 조건 | 파급 | 다음 검증 계획 |
```
**"내가 AI 제안을 거부하고 바꾼 지점"을 반드시 하나 이상 쓴다.** 이해 없이 받아쓴 게 아니라는 가장 강한 증거다.

**⑤ `SESSION-HANDOFF.md` — 소통 축(FDE 트랙)**

> 이름 주의: §3의 `mvp/HANDOFF.md`는 Opus에게 주는 구현 스펙이고, 이것은 사람·다음 세션에게 주는 인수인계 문서다. 둘을 섞지 않는다.

다른 사람 또는 다른 세션이 그대로 이어받을 수 있게 쓴다.
- 지금까지 한 일 / 지금 상태 / 다음 할 일
- 알려진 문제와 재현 방법
- 건드리면 안 되는 곳과 이유
- 실행 방법

인수인계 문서를 남긴 참가자가 유리하다.

### 4.3 주기적 자가점검

작업 중 일정 단위마다(모듈 완료·30~45분) 5축을 훑고 빈 곳을 경고한다.

```
⚠ 자가점검
 ① 기술   ○ 테스트 통과
 ② 의도   △ 의도 갱신 로그 2건 누락 (13:20 스코프 축소)
 ③ 인지   ✗ COGNITION.md 비어 있음 ← 전원 최저점 축
 ④ 소통   ✗ SESSION-HANDOFF.md 없음
 커밋     △ 최근 4건에 why/검증 누락
```

### 4.4 제출 후 확인 문제 대비

확인 문제는 모범답안이 **항상 3단계**로 생성되어 대조된다. 답변을 이 순서로 고정한다.

1. **내 코드의 구체적 약점 지점 지목** — 파일·함수·줄 단위로. 일반론 금지.
2. **그게 왜 위험한지 파급 설명** — 어떤 입력·상황에서 어떤 결과로 번지는가.
3. **다음에 뭘 검증·개선할지 계획** — 구체적인 검증 방법까지.

`COGNITION.md`의 "예상 리스크 3개" 표가 그대로 이 답변의 재료가 된다. 미리 써두면 현장에서 만들지 않아도 된다.

## 5. 마무리

1. `STATE.md` 갱신 → `current_stage: ④report`
2. `INDEX.md` 행 갱신
3. 사용자에게 보고: 구현된 시나리오, 제외한 것, 미해결 `[출처 필요]`·`[사용자 입력 필요]`, 남은 리스크

### ai-nativeness — ④를 쓰지 않는다

제출물이 코드·커밋·로그이므로 발표덱·제출문서 단계가 없다. 대신 **제출 직전 체크**를 하고 `current_stage: 완료`로 간다.

```
제출 직전 체크
 [ ] 5축 자가점검 전 항목 ○
 [ ] verification.log 마지막 실행이 현재 코드 기준인가
 [ ] INTENT.md 의도 갱신 로그가 실제 커밋 시각과 맞물리는가
 [ ] COGNITION.md에 "AI 제안을 거부하고 바꾼 지점" 1개 이상
 [ ] SESSION-HANDOFF.md로 지금 상태를 인수인계 가능한가
 [ ] 확인 문제 3단계 답변 초안 (COGNITION.md 리스크 표에서 파생)
 [ ] 빌드가 깨지지 않은 상태로 커밋되었는가
```
